# 분석 기록 — DT0503 시선 유지 (2026-11-17)

README의 작업 순서 1~6을 한 번에 돌린 기록. **무엇을 어떤 근거로 정했는지**를 남긴다.
수치는 `outputs/a_stats.txt`, `outputs/compare_stats.txt`에 그대로 있다.

## 0. 환경·데이터

- 이 PC는 리눅스라 `setup.ps1` 대신 같은 내용의 `setup.sh`를 새로 만들어 돌렸다.
  torch 2.11+cu128, RTX 5080 인식 확인.
- 설치 중 두 가지를 고쳤다.
  - `requirements.txt`의 `sam2 @ ...` → **`sam-2 @ ...`**. 공식 저장소 `pyproject`의 패키지
    이름이 `sam-2`라 pip이 이름이 다르다며 거절했다. `import sam2`는 그대로다.
  - 셸에 ROS 2 `PYTHONPATH`가 걸려 있어 pip과 스크립트가 `/opt/ros/...`의 numpy·cv2를
    먼저 집었다. `setup.sh`에서 `unset PYTHONPATH` 하고, 스크립트도
    **`env -u PYTHONPATH .venv/bin/python ...`**로 돌린다.
- 데이터는 이 PC에 이미 있었다. `data/drone_DT0503` → `~/usv_log/DT05/03/bag` 심볼릭 링크,
  `data/usv_DT0503` ← `~/usv_log/03.zip` 해제.

## 1. 추출 — `scripts/extract_bags.py`

bag 두 개 → `outputs/`의 CSV와 JPEG 956장.

- 카메라 내부 파라미터는 전 구간 한 값이었다: **fx=fy=625, cx=408, cy=272, 816×544**.
  따라서 **1° = 10.9 px** (README의 "5° ≈ 45 px" 근사보다 정확하다. 실제로는 5° = 54.7 px).
- 짐벌 틸트는 토픽으로 따로 안 온다. `/gcs/daiv/rd/command`의
  `[183(DO_SET_SERVO), ch9, pwm]`에서 `각도 = (pwm − 1500) / 5.5`로 되돌렸다
  (`usv_follow_node.servo()`의 역산).

## 2. 구간 정하기 — 왜 이 237초인가

`/gcs/daiv/usv/follow`가 true인 구간은 **11:00:27.7 ~ 11:04:24.8 (237.1 s)** 하나뿐이다.
그 뒤 11:06:25~11:06:47은 `/gcs/daiv/tag/follow`(AprilTag 추종)라 2.3.4의 GNSS 시선 유지가 아니다.

**대형은 선미 하나고 구간 안에서 바뀌지 않았다.** bag에 대형 번호가 안 남아서 기하로 판정했다 —
USV 기준 무인기의 상대방위가 전 구간 평균 **+137°**였다. 무인기가 쓴 USV 기수는
`euler heading + 보정`인데, 보정 −45°를 더하면 180°, 곧 선미다.
(보정이 −45°였다는 것은 이 기하 자체가 근거다. 10/1 커밋의 +90°를 쓰면 +47°가 되어
어느 대형에도 안 맞는다. 현장에서 파라미터로 바꾼 것으로 보인다.)
→ **README에 적힌 "대형 전환 구간"은 DT0503에 없다.** 앞먹임 효과의 근거로는 쓸 수 없다.

덧붙여 `e_ψ` 자체는 대형과 무관하다. 조준점은 USV 위치(est)이지 대형 목표점이 아니라서,
USV 기수 보정값이 틀려도 `e_ψ`는 영향을 안 받는다.

## 3. (A) — `scripts/analyze_a.py`

식은 제어기 코드(`ros2/.../usv_follow_node.py`의 `plan()`)에서 그대로 가져왔다.
`geo.py`는 `mav.py`의 좌표 함수를 복사한 것이다(같은 식이어야 재현이 된다).

    ψ_d = 무인기 → USV 방위,  e_ψ = relative_bearing(ψ_d, ψ)

두 가지로 냈다.

| | 쓰는 USV 좌표 | 뜻 |
|---|---|---|
| `e_psi` | USV bag의 **같은 시각** 좌표 | 실제 시선 오차. (B)와 맞댈 값 |
| `e_psi_ctrl` | 0.205 s 묵은 좌표를 (나이+0.5 s) 등속 외삽 | 제어기가 그때 본 오차 |

**교차검증**: 짐벌 틸트 명령에서 `usv_below`를 거꾸로 풀었더니 **7.59 m**가 나왔다.
런치 기본값 8.0 m와 맞는다 → 추출과 시각 정렬이 맞다는 뜻.
수평거리 평균 19.13 m / RMSE 1.25 m도 기존 수치(19.20 m, 1.20 m)와 맞는다.

결과: **e_ψ 평균 +0.14°, RMS 1.48°, 최대 8.44°** (최대는 11:00:27~57 초기 포착 구간).
`e_psi_ctrl` RMS 1.43°, 둘의 차 RMS 0.34° → 위치 갱신 지연이 시선에 남긴 몫은 작다.

## 4. (B) — `scripts/track_b.py`

SAM2.1 small, 첫 프레임(idx 3)에 박스 `(300,165,395,280)` 하나만 주고 끝까지 전파.
511장 전부 마스크를 찾았고 **재지정이 필요 없었다**(`--refine` 옵션은 넣어 뒀다).

**검수(순서 5)**: 넓이가 튄 프레임과 중심이 크게 뛴 프레임(28, 32, 33, 426, 433, 485, 486,
498, 499)을 전부 눈으로 봤고, 42프레임 간격 균일 표본 13장도 봤다. 전부 MAIV-1 위에 있다.
넓이가 변한 것은 압축 잡음과 노출 변화 탓이지 추적 실패가 아니다.
직접 보려면 **`outputs/b_overlay.mp4`** (마스크 겹친 영상, 노란 십자가 화면 중앙).

화면에 두 척이 나오는데, 위쪽 작은 배가 아니라 **가운데 빨간 표식의 쌍동선이 MAIV-1**이다.

## 5. 비교 — `scripts/compare.py`

여기서 **처음 세운 가정이 틀렸다는 게 드러났다.**

(A)와 (B)는 같은 양이 아니다. (A)는 **기수**에 대한 오차고, (B)는 **카메라 광축**에 대한
오차다. 둘 사이에 짐벌이 끼어 있다. 실제로 (B)의 변동(RMS 5.78°)이 (A)(1.26°)의 4.6배였다.

그래서 사슬을 모형으로 세우고 단계마다 설명되는 몫을 셌다.

| 벗겨낸 것 | 남는 변동 RMS |
|---|---|
| (B) 그대로 | 5.78° |
| − (A) `e_ψ` | 5.24° |
| − 짐벌 yaw가 기수를 **0.90 s 늦게** 따라옴 | 4.14° |
| − 기체 roll이 방위로 샘 (계수 **0.74**) | **2.77°** |
| (A) `e_ψ` 자체 | 1.26° |

- roll 계수 0.74는 **sin(틸트 42.5°) = 0.68**과 맞는다. 짐벌의 yaw 축만 기체에 붙어 있어,
  42° 내려본 상태에서 기체가 기울면 방위가 그만큼 새는 기하와 일치한다. 우연이 아니다.
- 모형과 (B)의 상관은 0.878 (원래 (A)-(B) 상관은 0.531).
- 고정 편의: 가로 −6.0°(짐벌 yaw 0이 기수가 아니라 "앱 켠 방향"이라서),
  세로 −3.7°. 세로는 영상에서 실제 수면 높이차를 **5.1 m**로 풀었는데 명령은 7.6 m를
  가정했다 → 2.5 m만큼 과하게 내려봐서 USV가 화면 위로 치우쳤다.

**영상 끊김**: 1초 넘게 빈 곳이 12군데, 합쳐 51 s(234 s 중)다. 중복 프레임은 없으니
녹화 누락이 아니라 전송이 끊긴 것이다. 그림에서는 그 구간 선을 끊어 그린다
(안 끊으면 직선이 되어 "오차가 가만있었다"처럼 보인다).

## 6. 논문에 쓸 결론

1. **기수 제어는 시선을 잘 유지했다** — `e_ψ` RMS 1.5°, 화면으로 16 px.
   제어기가 본 오차와 USV bag으로 낸 오차가 거의 같아, GNSS 오차나 위치 갱신 지연이
   시선을 망친 것이 아니다.
2. **화면에서는 더 흔들렸고(RMS 5.8°), 그 차이는 제어가 아니라 카메라가 기수를 따라오는
   사슬에서 생겼다** — 짐벌 yaw 지연 0.9 s와 틸트 42°에서의 roll 누출.
3. **고정 편의 두 개는 보정으로 없앨 수 있다** — 짐벌 yaw 기준점, `usv_below` 값.

README 분석표의 "(A)≈(B) → 제어, (A) 작고 (B) 큼 → GNSS/지연" 갈래는 **세 번째 경우를
빠뜨렸다**. 여기가 바로 그 경우다: (A) 작고 (B) 큰데, 원인은 GNSS도 지연도 아닌 **짐벌**이다.

## 남은 것 / 확인 필요

- `usv_below`를 8.0 m로 띄웠는지(런치 기본값) 그날 다른 값을 줬는지 확인하면 좋다.
  영상에서 푼 실제 높이차 5.1 m는 새만금 안벽 높이로 말이 되는지 봐야 한다.
- USV 기수 보정 −45°가 10/02에 쓰였다는 것은 기하로만 판정했다. 당시 현장 기록이 있으면 대조.
- 짐벌 yaw 지연 0.9 s는 이 한 비행에서 맞춘 값이다. 다른 비행에서도 같은지는 안 봤다.
