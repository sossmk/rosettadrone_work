> 답변은 **한국어로, 짧게**. 논문 문장은 사용자가 직접 쓰고, Claude는 근거·계산·검토를 맡는다.

## 0. 왜 하는가

- 그래프의 "영상 수평 편차"(빨강)는 SAM2로 잰 픽셀 편차를 각도로 바꾼 값이다. 식: **θ_h = atan((u − c_x) / f_x)**
- 그런데 f_x = 625는 **보정한 값이 아니다.** `video_node.py`에 박혀 있는 대략값(원본 기준 1250 × 축소 0.5)이고, 코드 주석에도 "±10%"라고 적혀 있다. 렌즈 왜곡도 0으로 가정했다.
- 해상도를 줄인 것 자체는 문제가 아니다. `video_node._scale_info()`가 camera_info도 같은 배율로 줄인다.
- 그래서 카메라를 실제로 보정해서 f_x, f_y, c_x, c_y와 왜곡계수를 얻은 뒤 각도를 다시 계산한다.
- **e_ψ(검정)는 영향을 받지 않는다.** 빨강의 크기만 바뀐다.

## 1. 보정할 때 지킬 것

| 항목 | 내용 |
|---|---|
| 영상 경로 | 10/2 시험과 **같은 경로**: 기체 → RosettaDrone → H.264 → `video_node`. SD 카드 4K 영상은 화각과 잘림이 달라서 쓰면 안 된다 |
| 해상도 | **원본 1632×1088로 보정한다.** `video_node`를 `-p scale:=1.0`으로 띄운다 |
| 카메라 설정 | 10/2와 같은 앱·카메라 모드. 스트림이 3:2였으니 같은 모드로 하고 줌은 쓰지 않는다 |
| 화질 | `-p jpeg_quality:=95 -p publish_fps:=5` 정도면 된다 |

### 보정 방법 (ROS 2 예시)

```bash
# 1) 영상 노드 — 원본 해상도로
ros2 run rd_bridge video_node --ros-args -r __ns:=/gcs/daiv \
  -p scale:=1.0 -p jpeg_quality:=95 -p publish_fps:=5

# 2) 압축 → raw 변환 (같은 PC 안에서만. 네트워크로 raw를 흘리면 회선이 죽는다)
ros2 run image_transport republish compressed raw --ros-args \
  -r in/compressed:=/gcs/daiv/cam/compressed -r out:=/gcs/daiv/cam/image_raw

# 3) 보정기 — 체커보드 '안쪽 꼭짓점' 수와 칸 크기(m)를 실제 판에 맞게
ros2 run camera_calibration cameracalibrator --size 9x6 --square 0.025 \
  --ros-args -r image:=/gcs/daiv/cam/image_raw -p camera:=/gcs/daiv
```

- 체커보드는 같은 폴더의 **`checkerboard_A4_9x6_25mm.pdf`**를 쓴다: A4 가로, 10×7칸, 안쪽 꼭짓점 9×6, 칸 25 mm. 위 명령의 `--size 9x6 --square 0.025`가 이 판에 맞춰져 있다. **실제 크기(100%)로 인쇄**하고, 아래 100 mm 눈금자로 배율을 확인한다. 칸이 25 mm가 아니면 잰 값을 `--square`에 넣는다. 종이는 판판한 판에 붙인다.
- 체커보드를 화면 **가장자리와 구석까지** 골고루, 기울여서도 보여준다. X·Y·Size·Skew 막대가 다 차면 CALIBRATE → SAVE를 누른다.
- 결과는 `/tmp/calibrationdata.tar.gz` 안의 **`ost.yaml`**이다. 이 파일을 Claude에게 준다.
- ROS 없이 하려면 프레임 30~50장을 저장해 OpenCV `calibrateCamera`로 돌려도 된다. 결과 형식만 맞추면 된다.

## 3. yaml을 받은 뒤 Claude가 할 일 (1번은 끝남 → 2번부터)

1. **왜곡 영향 확인**
   - `outputs/b_track.csv`의 마스크 중심 (u, v) 전부에 대해 각도를 두 가지로 계산한다.
     - (a) 보정 K만 쓴 값: atan((u − c_x)/f_x)
     - (b) 왜곡까지 제거한 값: `cv2.undistortPoints`로 (x_n, y_n)을 구한 뒤 atan(x_n)
   - (a)와 (b)의 차이를 RMS와 최대값으로 보고한다. USV는 중앙에서 최대 약 210 px 안쪽에 있었다.
   - **차이가 작으면** (기준: 약 0.3° 이하): 논문에는 간단한 식 θ_h = atan((u − c_x)/f_x) 하나만 쓰고, "보정한 f_x 사용, 렌즈 왜곡 영향 0.X° 이하로 무시" 한 줄을 넣는다. 사용자가 왜곡 식은 너무 무겁다고 했고, 발표 때 설명할 수 있어야 한다.
   - 차이가 크면 사용자와 다시 정한다.
2. **스크립트 수정**
   - `scripts/compare.py`와 `scripts/fig_paper.py`가 `camera_info.json` 대신 보정 yaml을 읽도록 고친다(K는 0.5배). 옵션으로 왜곡 제거도 넣는다.
   - **SAM2(`track_b.py`)는 다시 돌릴 필요가 없다.** 픽셀 중심은 그대로다.
3. **다시 돌리고 갱신할 수치**
   - 그래프(fig_gaze_paper)
   - 가로 편의(현재 −6.0°), 카메라 방위 지연(현재 0.90 s), roll 누출 계수(현재 0.74), 단계별 RMS(5.78 → 2.77°)
   - 세로 편차(현재 평균 −3.7°)와 거기서 푼 실제 h_below(현재 5.1 m)
4. 바뀐 값을 `분석기록.md`에 적는다.

## 4. 논문 쪽에서 정해진 것

- **픽셀 → 각도 식**: 3.2.x 평가 방법 문단에 넣는다. 식 번호는 (10)부터.
  - θ_h = tan⁻¹((u − c_x)/f_x), 세로도 쓸 거면 θ_v = tan⁻¹((v − c_y)/f_y)
  - 한글 수식: `theta _{h} = tan ^{-1} LEFT ( {u - c _{x}} over {f _{x}} RIGHT )`
  - 기호: (u, v) = USV 마스크 중심, (c_x, c_y) = 주점, (f_x, f_y) = 초점거리(px)
- **세로 편차도 넣는 방향**: 식(4) 틸트 검증. 평균 −3.7°는 h_below를 7.6 m로 가정했는데 실제가 5.1 m였기 때문이다.
- **짐벌 관련은 한 줄만 쓴다**: "DJI SDK의 짐벌 모드 YAW_FOLLOW에서는 짐벌 yaw가 기체 yaw를 따라가며, 따로 지정하지 않으면 이 모드가 기본값이다." 근거: https://developer.dji.com/api-reference/android-api/Components/Gimbal/DJIGimbal.html
  - 0.9 s를 언급하게 되면 "짐벌 지연"이 아니라 **"카메라 방위 지연"**으로 쓴다. 영상 프레임 시각이 관제소에서 디코딩한 뒤 찍히므로(`video_node`의 `header.stamp = now`), 영상 전송 지연이 섞여 있다.
  - 깊게 들어가지 않는다. 사용자가 "너무 잡아먹히면 안 된다"고 했다.
- **해석의 뼈대**
  - e_ψ RMS 1.3° → 기수각 제어(앞먹임 포함)는 잘 됐다.
  - 영상 편차가 더 큰 것은 카메라가 기수를 늦게 따라오기 때문이다. 제어기 문제가 아니다.
  - 앞먹임 추가가 옳았던 이유: 비례 제어만 쓰면 기수가 ψ̇_d/K_ψ만큼 뒤처진다(예: 20°/s ÷ 0.8 = 25°).
  - DT0503에는 대형 전환이 없다(선미 하나). 전환 효과를 이 비행으로 직접 보이지는 못한다.
- **참고문헌 추가 후보**: [9] SAM 2 — N. Ravi et al., "SAM 2: Segment anything in images and videos," arXiv:2408.00714, 2024. (보정 방법을 인용한다면 Zhang, 2000)
