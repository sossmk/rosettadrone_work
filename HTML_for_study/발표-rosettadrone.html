RosettaDrone 은 무엇이고, 제어는 어디서 도는가

두 가지만 확실히 하면 된다. RosettaDrone 은 DJI SDK 와 MAVLink 사이의 번역기라는 것, 그리고 자율 제어는 앱이 아니라 우리 PC 의 ROS2 노드에서 돈다는 것. 나머지는 이 둘의 각주다.

왼쪽 구간은 DJI 독점 규격(OcuSync)이라 우리가 손댈 수 없다. RosettaDrone 은 조종기 안에서 도는 안드로이드 앱이고, 그 끝단에서 MAVLink 를 Wi-Fi UDP 로 내보낸다. 오른쪽이 우리가 만든 전부다.

한 문장

RosettaDrone 은 닫혀 있던 DJI 를 MAVLink 생태계에 연결하는 어댑터다. 자율 비행 로직은 들어 있지 않다 — 그건 우리가 ROS2 쪽에 만들었다.

역할 — 이름 그대로 로제타석

DJI 는 자사 SDK 로만 열려 있어서 QGroundControl·PX4 계열 도구가 말을 걸 수 없다. RosettaDrone 이 그 사이에서 양방향 통역을 한다.

실행 위치가 중요하다. 앱은 RM500 조종기 안에서 돈다. 드론에 올라가는 컴패니언 컴퓨터가 아니다. 그래서 드론과의 구간은 그대로 DJI 무선이고, 우리와의 구간만 표준 MAVLink 가 된다.

"RC 의 가상 조이스틱 아닌가?" — 절반만 맞다

MAVLink 명령마다 앱이 호출하는 DJI API 가 다르다. Virtual Stick 은 그중 하나일 뿐이다.

들어온 MAVLink앱이 호출하는 DJI APIVirtual Stick?

정확한 표현은 "MAVLink 명령을 DJI SDK 의 알맞은 API 로 라우팅하는 번역기이고, 그중 속도 명령 경로만 Virtual Stick 을 쓴다"이다. 우리 USV·태그 추종이 하필 그 속도 경로라서 "조이스틱 같다"는 인상이 강할 뿐이다.

RC 가 여전히 상위 권한이다

Virtual Stick 은 실물 스틱을 대체하지 않는다. RC 가 양보한 동안만 동작한다.

  • P 모드에서만 허용 — 다른 모드로 돌리면 앱이 명령을 버린다
  • 앱의 Safety 버튼을 누르면 Virtual Stick 을 끄고 RC 로 즉시 복귀
  • 우리 link_node 는 /gcs/daiv/cmd_vel 이 오기 전까지 #84 를 한 발도 쏘지 않는다 — 앱은 #84 를 받는 순간 Virtual Stick 을 켜기 때문이다

mav.py 는 오픈소스 라이브러리가 아니다

발표 전에 꼭 정정할 것

두 가지가 섞여 있다.

  • 앱 안의 오픈소스 — com.MAVLink (MAVLink 공식 Java 생성 코드)가 RosettaDrone 앱에 포함돼 있다. "오픈 라이브러리"라고 부를 만한 건 이쪽이다.
  • PC 쪽 mav.py — 우리가 직접 쓴 200줄짜리 자체 구현이다. pymavlink 를 일부러 쓰지 않았다. 이유는 파일 첫 줄에 적혀 있다: "새 PC 에서 pip 없이도 바로 돌아야 한다" — 표준 라이브러리만 쓴다.

"mav_py 라는 오픈소스를 썼다"고 말하면 질문이 들어왔을 때 곤란해진다. "MAVLink v2 인코딩을 의존성 없이 직접 구현했다"가 사실이고, 오히려 더 좋은 발표 재료다.

제어는 3단으로 겹쳐 있다

① 바깥

우리 P 제어 — PC 의 ROS2 노드, 20Hz. 위치 오차를 속도 명령으로 바꾼다. 발표에서 "우리가 만든 제어"는 전부 이것이다.

② 중간

link_node — 제어가 아니다. 안전 포화(속도 상한)와 데드맨만 건다. /gcs/daiv/cmd_vel 이 0.3초 끊기면 0 을 1초 쏘고 입을 닫는다.

③ 안쪽

DJI 비행제어기 — 속도 명령을 받아 자세와 모터를 맞춘다. 비공개다. 우리가 볼 수 없고 손댈 수도 없다. 앱은 모드만 잡아 준다: roll/pitch = VELOCITY, vertical = VELOCITY, yaw = ANGULAR_VELOCITY.

"안쪽이 P 제어"라는 인식은 반만 맞다. P 제어는 ① 우리 쪽이고, ③ 안쪽은 DJI 의 비공개 제어기다. 우리가 P 만 쓰고 I·D 를 안 쓰는 이유도 여기 있다 — 속도 추종은 ③ 이 이미 해 주므로, 우리는 위치 오차를 속도로 바꾸는 사상만 담당한다.

앱 안에도 yaw PID 가 하나 있지만 우리 경로에서는 비활성이다. #84 마스크에 YAW_IGNORE 비트를 켜서 우회하고, 우리 각속도 명령이 그대로 통과한다.

세 노드는 형제다 — /gcs/daiv/nav/goal 을 거치지 않는다

셋 다 각자 오차를 계산해 직접 /gcs/daiv/cmd_vel 에 쓴다. 같은 토픽을 공유하므로 동시에 켜면 안 된다. USV 추종이 nav_node 를 재사용하지 않은 이유는 뒤에 나올 feedforward 항과 기수 제어 때문이다 — nav_node 에는 둘 다 없다.

공통 P 제어

세 노드의 뼈대는 같다. 20Hz 로 돌면서 오차를 구하고, 비례 상수를 곱하고, 상한으로 자른다.

v = min(v_max, Kp · e) 수평 — 크기에서 자르고 방향은 보존 vz = clamp(Kp_alt · e_alt, ±vz_max) wz = clamp(Kp_yaw · e_yaw, ±yaw_max)

적분·미분 항이 없다. 위치 오차를 속도로 사상하는 단계라서 닫힌 루프가 1차계가 되고, 오버슈트 없이 지수적으로 수렴한다.

포화 구간 (d > v_max/Kp = 2.5/0.35 ≈ 7.1 m) → 등속 2.5 m/s 선형 구간 (d < 7.1 m) ḋ = −Kp·d → d(t) = d₀·e^(−Kp·t) 시정수 τ = 1/Kp ≈ 2.9 초

실제 대역은 GPS 가 정한다

제어는 20Hz 로 돌지만 위치 피드백(#33)은 5Hz 로 온다. 같은 좌표로 4 tick 을 도는 셈이라 실효 제어 대역의 상한은 5Hz 다. Kp = 0.35 가 보수적인 것이 이것과 맞물린다 — 더 올리면 샘플링·링크 지연 때문에 진동한다.

nav_node — GPS 경유점

목표 좌표까지의 거리와 방위를 구면 기하로 구하고, 기수 기준 상대각으로 돌려 속도 성분으로 나눈다.

d = 거리(우리, 목표) haversine θ = 방위(우리 → 목표) 0 = 북, 시계 ψ = wrap(θ − 기수) 기수 기준 상대각 s = min(v_max, Kp · d) vx = s · cos ψ 앞 vy = s · sin ψ 오른쪽 vz = clamp(Kp_alt · (목표고도 − 현재고도), ±vz_max)

도착 판정은 d < 1.0 m 이고 고도 오차도 1m 안이어야 한다. 경유점이 여러 개면 중간점에서는 속도 0 을 내지 않는다 — 내면 link_node 의 데드맨이 걸려 매 점마다 멈칫하기 때문이다. 그 tick 만 건너뛰면 직전 속도가 유지된 채 다음 점으로 넘어간다.

tag_follow_node — AprilTag

검출은 우리 코드가 아니라 apriltag_ros 패키지가 한다. 36h11 계열, 인쇄물 실측 192mm, PnP 로 6-DoF 자세를 풀어 /tf 로 낸다.

여기서는 좌표 변환이 필요 없다. 카메라가 이미 기체 기준 오차를 직접 주기 때문이다 (짐벌 −90° 탑뷰 전제).

앞 = −y 화면 위가 기수 앞 오른쪽 = +x 고도오차 = z − 유지고도 yaw 오차 = (태그 x축이 기수에서 돈 각) − 90° d = √(앞² + 오른쪽²) d < 0.3 m → 정지 (불감대) 그 외 → s = min(v_max, max(v_min, Kp·d)), 방향은 (앞, 오른쪽)

min_speed 하한이 nav_node 에 없는 항이다. 가까워지면 Kp·d 가 기체가 반응하지 못할 만큼 작아지므로 하한을 두고, 대신 불감대로 진동을 끊는다.

usv_follow_node — 목표 결정과 추종

USV 좌표를 그대로 쫓지 않는다. 네 단계를 거친다.

1. 속도 추정

최근 2초 창의 양 끝 두 점만으로 유한차분. 중간 점을 버리는 것이 가장 싼 저역통과다. 두 점 간격이 0.5초 미만이면 0 으로 본다 (GPS 잡음 증폭 차단).

(v_N, v_E) = (거리·cos방위, 거리·sin방위) / Δt
2. 외삽

받은 좌표는 이미 과거다. 등속으로 앞당긴다.

T = age + lead_secs age = 좌표가 온 지 지난 시간, lead = 0.5초 p̂ = USV 좌표 + (v_N·T 북, v_E·T 동)

age 는 이미 흐른 지연을, lead_secs 는 앞으로 흐를 지연(제어 주기 + 링크 + 기체 응답)을 보상한다. 등속 가정이라 USV 급선회 중에는 바깥쪽으로 벗어난다 — 한계로 코드에 명시해 뒀다.

3. 목표점

추정 위치에서 대형만큼 떨어뜨린다. 기준이 지도 방위가 아니라 USV 기수라서, USV 가 돌면 목표점도 따라 돈다.

목표 = p̂ 에서 (앞 f₁, 오른쪽 f₂) 만큼 ← USV 기수 기준으로 회전 기본 대형 1번 = 왼쪽 10m 2번 = 오른쪽 10m 3번 = 뒤 10m (셋 다 고도 5m)
4. 제어

nav_node 와 같은 P 에 USV 속도 feedforward 를 더한다.

vx = s·cos ψ + v_N·cos h + v_E·sin h vy = s·sin ψ − v_N·sin h + v_E·cos h └─ P 항 ─┘ └─── feedforward ───┘ h = 우리 기수 합친 뒤 크기로 포화 (방향 보존) 기수: wz = clamp(Kp_yaw · (p̂ 방위 − h)) ← 목표점이 아니라 USV 본체를 본다

feedforward 가 발표의 핵심 수식이다

P 제어만으로 등속 목표를 쫓으면 정상상태 오차가 남는다.

FF 없음: Kp · e_ss = v → e_ss = v / Kp USV 2.0 m/s, Kp = 0.35 → 5.7 m 뒤처짐 USV 2.5 m/s → 7.1 m — 속도 상한에 걸려 사실상 추종 실패 FF 있음: v_cmd = Kp·e + v → e_ss = 0

적분항 대신 feedforward 를 쓴 이유: I 항은 위상 지연과 와인드업을 가져오지만, FF 는 지연 없이 즉시 상쇄한다. 목표의 속도를 이미 측정하고 있는 상황이라 FF 가 정답이다.

짐벌 틸트 — arctan 맞다

질문하신 대로 순수 기하다. 피드백이 없는 완전 개루프다 — 짐벌의 실제 각도를 되읽지 않는다.

틸트 = −atan2( 우리 상대고도, 우리 ↔ 추정 USV 수평거리 ) 클램프 [−90°, 0°] 0 = 수평, −90 = 바로 아래

수평거리는 목표점이 아니라 추정 USV 위치까지다. 기수 제어도 마찬가지다 — 목적이 이동이 아니라 카메라 겨눔이라서, 뒤 10m 대형이면 기수와 카메라는 앞쪽 USV 를 향해야 한다.

전송은 DO_SET_SERVO 채널 9 로 하고, 값은 1500 + 틸트 × 5.5 다. 5.5 는 임의의 상수가 아니라 앱의 역변환을 그대로 맞춘 것이다 — 앱이 (값 − 1500) / 5.5 로 되돌려 짐벌 절대각으로 넣는다. 짐벌 yaw(채널 8)는 앱 구현이 상대·누적각이라 절대 지령이 불가능해서 쓰지 않고, 대신 몸체를 돌린다.

2° 이상 바뀔 때만, 최대 2Hz 로 보낸다. 짐벌 회전 명령이 2초에 걸쳐 도는 형태라 고빈도로 쏘면 이전 회전을 계속 끊어먹는다.

예상 질문

제어를 드론 위가 아니라 PC 에서 돌리면 지연이 문제 아닌가?

그래서 세 겹으로 막는다. ① 20Hz 로 계속 갱신한다 — #84 한 발의 효력은 200ms 라 끊기면 자동으로 무효가 된다. ② link_node 데드맨: /gcs/daiv/cmd_vel 이 0.3초 끊기면 0 을 1초 쏜다. ③ 각 노드가 입력 신선도를 보고 스스로 멈춘다. 그리고 실제 병목은 링크가 아니라 GPS 5Hz 다.

왜 PID 가 아니라 P 인가?

속도 추종은 DJI 비행제어기가 이미 한다. 우리 단계는 위치 오차를 속도로 바꾸는 사상이라 P 만으로 1차 수렴이 나온다. 움직이는 목표의 정상상태 오차는 I 항 대신 feedforward 로 없앴다 — 지연도 와인드업도 없다.

RC 조종사는 무엇을 할 수 있나?

언제든 가져갈 수 있다. Virtual Stick 은 P 모드에서만 허용되고, 모드를 돌리거나 앱의 Safety 버튼을 누르면 즉시 RC 로 돌아온다. 자율 명령은 RC 가 양보한 동안만 유효하다.

태그 추종과 USV 추종을 같이 쓸 수 있나?

지금은 안 된다. 둘 다 /gcs/daiv/cmd_vel 에 쓰기 때문에 동시에 켜면 서로 덮어쓴다. 두 방식을 섞으려면 조정 노드가 하나 더 필요하다.
